# Pandora-RAG 预实验结果报告

## 1. 实验设置

- 数据集：HotpotQA `distractor`
- 采样规模：训练集 `1000` 条，测试集 `500` 条
- 最大检索步数：`K=5`
- 单步虚拟成本：`c=0.05`
- 生成模型：`qwen2.5:7b`
- 运行方式：离线缓存完整轨迹，再做停止策略模拟

本次预实验分为三步：

1. 收集每个问题在 `1~5` 步检索下的完整 RAG 轨迹；
2. 用训练集估计 Weitzman 保留值，验证 Oracle 停止策略；
3. 用浅层特征训练轻量 Probe，验证是否可以替代 Oracle。

总耗时约 `9912.8s`，其中轨迹收集约 `9907.6s`，其余分析耗时很小。

## 2. Step 1: 轨迹统计

测试集上，固定步数策略的平均 F1 随检索步数增加而上升：

| 策略 | 平均步数 | 平均 F1 | 平均 EM |
| --- | ---: | ---: | ---: |
| Always-K=1 | 1.000 | 0.3925 | 0.2980 |
| Always-K=2 | 2.000 | 0.4816 | 0.3660 |
| Always-K=3 | 3.000 | 0.5242 | 0.4000 |
| Always-K=4 | 4.000 | 0.5400 | 0.4100 |
| Always-K=5 | 5.000 | 0.5535 | 0.4300 |

附加观察：

- 从 `K=1` 到 `K=5`，平均 F1 提升 `+0.1610`，说明多步检索整体有效。
- `500` 个测试样本中，最佳答案出现在第 `1` 步的有 `340` 个，占 `68.0%`。
- 最佳答案出现在第 `2/3/4/5` 步的样本分别有 `83/42/22/13` 个。
- `K=5` 相比 `K=1` 有 `138` 个样本提升、`38` 个样本退化、`324` 个样本基本不变。

这说明两点同时成立：

- 更多检索通常能提升平均性能；
- 但继续检索并不总是有益，后续步骤会让一部分样本答案变差，因此“何时停止”确实是值得研究的问题。

## 3. Step 2: Oracle 停止策略结果

训练集估计得到的保留值为：

| 步数 k | 保留值 r_k |
| --- | ---: |
| 1 | 0.8677 |
| 2 | 0.5965 |
| 3 | 0.2472 |
| 4 | 0.0894 |
| 5 | -0.0015 |

测试集上的 Oracle 结果如下：

| 策略 | 平均步数 | 平均 F1 | 平均 EM |
| --- | ---: | ---: | ---: |
| Always-K=5 | 5.000 | 0.5535 | 0.4300 |
| Oracle-Pandora-RAG | 2.328 | 0.6111 | 0.4660 |

核心结论：

- Oracle 只用 `2.328` 步，较 `Always-K=5` 节省 `53.4%` 的检索成本。
- Oracle 的平均 F1 达到 `0.6111`，比 `Always-K=5` 还高 `+0.0576`。
- Oracle 的平均 EM 也从 `0.4300` 提升到 `0.4660`。

这说明 Pandora-style stopping 在这个离线 RAG 场景下是成立的。原因并不是“少检索更强”，而是：

- 多检索能提高上限；
- 但检索过头会让部分样本答案退化；
- 如果能在正确的时机停止，就能同时拿到更低成本和更高质量。

因此，这个预实验已经较强地支持了项目的核心理论假设：**停止决策不是玄学，而是有显著收益的。**

## 4. Step 3: 轻量 Probe 结果

Probe 使用的特征为：

- `mean_logprob`
- `entropy`
- `token_count`
- `bm25_score`
- `step`

模型表现：

- 5 折交叉验证 `R² = 0.2726 ± 0.0162`
- 测试集 `MAE = 0.3505`
- 测试集 `R² = 0.1341`

停止策略对比如下：

| 策略 | 平均步数 | 平均 F1 | 平均 EM |
| --- | ---: | ---: | ---: |
| Fixed-τ=0.3 | 2.576 | 0.6243 | 0.4720 |
| Fixed-τ=0.5 | 2.716 | 0.6281 | 0.4820 |
| Fixed-τ=0.7 | 3.172 | 0.6218 | 0.5040 |
| Probe-Pandora-RAG | 1.918 | 0.4811 | 0.3700 |
| Oracle-Pandora-RAG | 2.328 | 0.6111 | 0.4660 |

这里要特别注意解释：

- `Probe-Pandora-RAG` 只达到 Oracle 的 `78.7%`，说明当前浅层特征还不足以稳定预测答案质量。
- 它虽然把平均步数压到 `1.918`，但 F1 只有 `0.4811`，基本退回到 `Always-K=2` 水平。
- 表中 `Fixed-τ` 看起来比 Oracle 还强，但这是一个**乐观上界**，因为实现里直接用了真实 `F1` 作为停止信号，这在真实部署中不可用。

所以，Step 3 的正确结论不是“简单 Probe 已经足够”，而是：

- 当前这版轻量 Probe 还不够好；
- 理论上限已经被 Step 2 验证；
- 下一阶段工作的重点应转向“如何更准确地预测当前质量或未来增益”。

## 5. 总结

本次预实验给出的结论可以概括为：

1. 多步检索有价值，`K=5` 明显优于 `K=1`。
2. 继续检索并不总是有益，存在明显的“过检索退化”现象。
3. Oracle-Pandora-RAG 证明了停止策略有很强潜力：在少一半以上检索成本的情况下，F1 和 EM 反而更高。
4. 当前版本的轻量 Probe 还不足以复现 Oracle 效果，因此“理论可行”已经得到支持，但“轻量可学”这一点暂时没有被本次结果充分支持。

如果把这次预实验作为项目立项阶段的判断依据，那么比较稳妥的表述是：

> Pandora-RAG 的核心思想在离线 Oracle 设定下已经被明确验证，值得继续推进；但可部署的停止器目前仍需更强特征、更好校准方式，或直接预测未来增益而非当前 F1。

## 6. 建议的下一步

- 改进 Probe 目标：从预测当前 `F1` 改为预测下一步期望增益 `E[G_{k+1}]`。
- 增加更强特征：答案长度、检索文档重叠率、前后步答案变化率、自一致性信号等。
- 重新设计基线：避免使用真实 F1 作为固定阈值信号，改为只使用可部署特征。
- 输出更多可视化：补充 Oracle 停止步数分布图、Probe 预测误差图和策略 Pareto 图到汇报材料中。

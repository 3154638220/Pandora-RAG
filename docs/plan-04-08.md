### 当前最优 Probe 性能（Test）


| 数据集      | Probe F1  | Probe 步数 | Deployable-GW F1 | D-GW 步数 | Original-GW F1 (参照) | Oracle F1 |
| -------- | --------- | -------- | ---------------- | ------- | ------------------- | --------- |

**核心结论**：Probe 在三数据集上均显著优于公平基线 Deployable-GW，但与 Original-GW（半 Oracle，使用真实 F1 停止）仍有显著差距。D1+D2 诊断一致表明 **特征信号不足是主瓶颈**，而非模型架构或训练技巧。

### 关键瓶颈诊断

1. **特征信号弱**：20 维浅层中，多数特征单变量 AUROC < 0.60；`answer_logprob` 在 hotpotqa 上仅 0.26，`self_eval_score` 普遍 < 0.50
2. **XGB ≈ MLP**：同特征下 XGBoost 未系统性优于 MLP，排除模型侧为主因
3. **Hidden 分支增益微弱**：4096→64 的压缩可能过于激进，shallow-only 与 full 差距仅 +0.02~0.05
4. **Deployable-GW 过早停止**：self_consistency 作为代理在第 1 步即触发停止，实际部署中该基线退化为 Fixed-K=1

## 二、下一步行动（按优先级排列）

### P0（最高优先级）：在已有 `answer_logprob` 上继续「做细」⬅️ 可选主攻

**澄清（避免与旧计划混淆）**：**均值标量 `answer_logprob` 已经接入**——`pretest/utils/llm_client.py` 写入平均 token logprob，Stage1 落盘，Stage2 的 `SHALLOW_FEATURE_NAMES` 含该列（20 维之一）。这与 `docs/stage2_next_steps_analysis.md` 一致。

**尚未做的**是文档里写的 **logprob 系列扩展**：例如 `answer_logprob_min`、`answer_logprob_std`、以及把 `answer_logprob` 纳入 `_delta_source_scalars` 得到步间 `delta_answer_logprob`（当前差分只对 retrieval_score、semantic_entropy 等 5 个量计算，**不含** logprob）。

**动机**：D1 显示**现有单列** `answer_logprob` 在 hotpotqa 上单变量 AUROC 仍弱（≈0.26），因此「再落盘 min/std + 可选 delta」是**增量工程**，不是从零补字段。

**具体任务**：

1. **Stage1 侧追加 logprob 统计量**（在已有 `answer_logprob` 旁扩展，非替换）：
  - `answer_logprob_min`：最低置信 token 的 logprob（捕捉局部不确定性）
  - `answer_logprob_std`：token 级 logprob 标准差（量化置信度一致性）
  - 确保 `pretest/utils/llm_client.py` 在支持 logprobs 的后端上稳定返回 token 级数据，fallback 值不会大面积稀释特征
2. **Stage2 侧接入新维度**：
  - `SHALLOW_FEATURE_NAMES` 扩展（min、std 等）；若要对 logprob 做步间差分，需**显式扩展** `_delta_source_scalars` / `_step_shallow_features`（当前不会「自动」为新区加 delta）
  - `SHALLOW_FEATURE_DIM` 同步更新
3. **验收链路**：
  - `run_feature_diagnostic` → 确认新维度 AUROC
  - `run_stage2` → 对比当前 20 维基线的 test F1
  - 目标：至少 1/3 数据集 Probe F1 有 > 0.01 的正向提升

**预计工作量**：1–2 天（Stage1 改轨迹写入 + Stage2 扩维 + 全量重训）

---

### P1（高优先级）：改进 `self_eval_score` 测量质量

**动机**：当前 `self_eval_score` 单变量 AUROC 在三数据集上均 < 0.50，可能源于 prompt 设计或量表粒度。与 `self_consistency` 的相关性需要验证——若高度共线，则二者占用容量但贡献冗余。

**具体任务**：

1. **Prompt 审计与改进**：
  - 审查 `pretest/utils/llm_client.py` 中 `SELF_EVAL_PROMPT`，评估是否需要调整量表（当前 1-5 分 → 考虑 1-10 或二值化）
  - 测试改进后的 prompt 在小样本上的分布和与 EM/F1 的相关性
2. **共线性分析**：
  - 计算 `self_eval_score` 与 `self_consistency`、`semantic_entropy` 的 Pearson/Spearman 相关系数
  - 若 |r| > 0.8，考虑只保留区分力更强的一个，释放维度给其他信号
3. **端到端验收**：改进后重跑 Stage1（仅 self_eval 相关步骤） → D1 诊断 → Stage2 全量

**预计工作量**：1–2 天（视是否需重跑 Stage1 轨迹）

---

### P2（中优先级）：D6 简化模型基线（论文消融）

**动机**：论文叙事需要「非线性是否必要」的消融证据。D6 本身不以涨点为目的，而是为论文完整性服务。

**具体任务**：

1. **逻辑回归基线**：
  - 使用 scikit-learn `LogisticRegression` + 同一 20 维浅层特征 + 同一 Phase C 阈值逻辑
  - 输出：test F1 / steps / cost，与 MLP / XGBoost 并排对比
2. **线性 Probe（hidden-only）**：
  - 在 4096 维 hidden states 上直接做线性二分类
  - 验证「深层特征的线性可分性」
3. **Top-5 特征逻辑回归**：
  - 从 D1 诊断中选 AUROC 最高的 5 个特征，训练逻辑回归
  - 为论文「特征选择 vs 全量」提供数据

**产出**：`docs/stage2_report_d6.md`、`results/stage2_d6_baselines.json`

**预计工作量**：0.5–1 天

---

### P3（中优先级）：Hidden 分支改进探索

**动机**：当前 hidden 分支（4096→64 压缩 + LayerNorm）增益仅 +0.02~0.05。可能的改进方向：

**候选方案**（按投入产出比排序）：

1. **提升压缩维度**：`compress_dim` 从 64 提升到 128 或 256，减少信息损失
2. **多层 hidden 融合**：不只取最后一层，而是取最后 4 层的加权平均（需 Stage1 额外落盘）
3. **注意力池化**：替代 last_token，用简单的 attention pooling 聚合序列表征

**决策依据**：若 P0 的 logprob 扩展带来显著增益，hidden 分支优先级可降低；反之则需投入。

**预计工作量**：1–3 天（取决于是否需要 Stage1 重跑）

---

### P4（阶段性目标）：Stage3 — E-value 风险控制

**前置条件**：P0–P2 完成后，Probe 在可部署口径下性能稳定。

**核心内容**（参考 `experiments.md` 第三阶段）：

1. **误差定义**：样本 $t$ 发生 Error $\iff$ F1($s_{\tau_t}$) < γ（如 γ=0.5）
2. **Betting Score 构造**：在 Calib 集上训练轻量质量预测器，预测 $P(\text{F1} \geq \gamma)$
3. **E-process 工程落地**：
  - 维护累积乘积 $E_n = \prod_{t=1}^n e_t$
  - 动态安全阀：当 Probe 的 Stop 决策可能导致 $E_n$ 突破安全边界时，强制继续检索
4. **核心测试**：
  - 设置 α=0.1, 0.2
  - 绘制 Empirical Error Rate 随样本数 n 的变化曲线
  - **对比标准 CP**：证明 CP 在自适应停止下覆盖率崩溃，而 E-value 保持 anytime-valid

**产出**：`stage3/` 模块代码、`docs/stage3_report.md`、E-value 轨迹图

**预计工作量**：5–7 天

---

### P5（最终目标）：Stage4 — 主实验与论文表格

**前置条件**：Stage3 落地且 E-value 验证通过。

**核心内容**：

1. **端到端对比矩阵**：Fixed-K、IRCoT、Stop-RAG、ITER-RETGEN、Global-Weitzman、Deployable-GW、Oracle、Pandora-RAG（Probe + E-value）
2. **泛化性测试**：HotpotQA 训练的 Probe → zero-shot MuSiQue，验证 E-value 安全阀的跨域鲁棒性
3. **论文核心表格与图**：
  - 主表：策略 × {F1, EM, Avg Steps, Cost, Error Rate}
  - Pareto Frontier 图（含 E-value 约束后的位置）
  - E-process 动态防御轨迹图

**预计工作量**：3–5 天

## 四、风险与应对


| 风险                                | 影响                  | 应对                                                      |
| --------------------------------- | ------------------- | ------------------------------------------------------- |
| logprob 扩展后仍无显著增益                 | P0 失败，需转向 hidden 改进 | 立即启动 P3；同时评估 P1 self_eval 是否有独立贡献                       |
| self_eval 与 self_consistency 高度共线 | 浅层维度浪费              | 去除冗余维度，释放给其他信号（如 reference model NLL）                   |
| Stage3 E-value 过于保守（全部跑满 5 步）     | 成本指标退化              | 调整 Betting Score 函数、引入信用盈余机制或折现因子                       |
| 目标会议 EMNLP 2026 投稿 deadline 临近    | 时间紧张                | P0+P2+P4 为最小可投稿路径；P1/P3 可后置到 camera-ready               |
| vLLM 后端不稳定返回 logprobs             | P0 特征质量差            | 在 `llm_client.py` 中加强 fallback 检测与日志，切换到支持 logprobs 的后端 |

## 六、当前不建议投入的方向

1. **继续在同特征上调 MLP 超参**：D2（XGB ≈ MLP）已证明模型侧不是瓶颈
2. **以 Original-GW 为 KPI 做迭代**：口径不公平（半 Oracle），会误导工程决策
3. **大幅增加浅层拼接维度而不改数据源**：边际递减严重，优先改 Stage1 观测量
4. **提前实现 PPO 联合微调**：属 experiments.md 中的 Optional 方案，在 Probe + E-value 验证完成前不应分散精力
